# Metis 工作台 UI/UX 与设计系统工程化调研

调研日期：2026-11-23。

本文回答五个相互关联的问题：如何形成优秀的体验与视觉品味，如何用方法论和流程保持长期一致，如何扩展而不反复重做，如何让骨架与主题独立演进，以及这些方案能否由当前的 GPUI 技术栈落地。调研分为产品基准、设计系统、Human-AI 交互、可访问性和 GPUI 实现五条线，经过多轮官方资料与固定版本源码核查。

文中将外部资料确认的**事实**与面向 Metis 的**建议**分开。未单独标注日期的网页访问日期均为 2026-11-23。候选视觉参数不是已经批准的设计规范；本次没有完成高保真原型、目标用户测试或真实屏幕阅读器验收，因此不能据此宣称“最佳设计”或“已经符合 WCAG”。

## 一、结论

建议采用一套**受控扩展的语义化设计系统**，而不是先画一套静态皮肤，也不是先建设庞大的组件库。

这套系统由六部分组成：

1. 能裁决方案取舍的体验原则；
2. 稳定、诚实的产品状态与动作语义；
3. 可组合的工作台骨架和交互模式；
4. 有明确行为、状态和无障碍契约的组件；
5. 将视觉值与产品语义分开的设计令牌；
6. 覆盖评审、测试、发布、迁移和治理的持续流程。

对本次五个目标的直接回答如下：

| 目标           | 结论                                                                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 方法论与流程化 | 用“原则 → 真实任务 → 压力测试 → 契约 → 垂直实现 → 验证 → 版本化演进”作为主流程；双钻和 Atomic Design 只作为辅助工具。                              |
| 优雅与用户体验 | 借鉴 Linear 的视觉权重、密度和克制，Raycast 的动作闭环，Zed 的原生工程经验，Primer 的状态与无障碍；不复制任何产品的皮肤。                          |
| 可扩展         | 稳定语义、组件契约、动作注册表和工作台区域，允许组合与有限布局变体；不为假想需求预先建立万能抽象。                                                 |
| 长期一致       | 令牌、组件、模式和主题都有负责人、生命周期、测试与迁移规则；例外必须有范围和回收条件。                                                             |
| 骨架与主题分离 | 页面和组件消费语义令牌，主题只替换令牌值；信息架构、区域语义、内容、动作、键盘行为和状态含义不随主题改变，字体和密度触发的重排必须保留当前上下文。 |

这里最重要的边界是：**可扩展不等于什么都可以配置，长期稳定也不等于像素永远不变。** 应优先稳定用户已经形成的语义和肌肉记忆，同时允许视觉值、局部组合和实现持续改进。

## 二、方法论：组合使用，但不迷信单一模型

### 2.1 各方法适合解决的问题

**双钻适合探索新问题，不适合充当组件工程流程。** Design Council 将 Discover、Define、Develop、Deliver 描述为发散与收敛，并明确它不是线性过程，交付后仍持续反馈。[Framework for Innovation](https://www.designcouncil.org.uk/resources/framework-for-innovation/) 可用于研究“多主机智能体如何让用户保持控制”，不必套在每次按钮修订上。

**Atomic Design 适合同时检查局部与整体，不适合按原子到页面的顺序施工。** 原作者明确说它不是线性流程，页面应装入真实代表性内容，反过来检验组件和模板。[Atomic Design Methodology](https://atomicdesign.bradfrost.com/chapter-2/) Metis 可以使用更直观的“基础组件 / 产品组件 / 交互模式 / 页面骨架”命名，不必让化学分类决定 Rust 模块。

**设计系统应作为长期产品维护。** Primer 将主题适配、交互测试、视觉回归、无障碍、生产使用和迁移路径纳入组件成熟度，而不是“代码能运行即稳定”。[Primer Component Lifecycle](https://primer.github.io/contribute/component-lifecycle/) Carbon 的稳定性清单同时覆盖令牌、状态、溢出、焦点流、组合、文档和测试。[Carbon Component Checklist](https://www.carbondesignsystem.com/getting-started/contributing/component-checklist)

**Human-AI 准则是 Metis 不可缺少的一层。** Microsoft HAX 要求根据上下文决定何时打断，支持高效退出、纠正和恢复，说明行为原因及用户动作后果，并提供全局控制。[HAX Design Library](https://www.microsoft.com/en-us/haxtoolkit/library/) 这些要求比通用的“简洁美观”更能决定智能体工作台是否可信。

### 2.2 建议的主方法

采用“**设计系统作为长期产品 + 端到端垂直切片**”。不要先把所有色板、按钮和面板做完，再验证完整工作流；第一条切片就贯穿冷启动与环境准备、添加并打开本地项目、会话、流式输出、审批和差异审查，并同时覆盖加载、空、启动失败、无效目录、错误恢复和重连状态。

一条切片只提取当前真实需要的组件和令牌。新模式先在具体页面或 Preview 中验证，经多个真实使用场景确认后再晋升为 Stable，避免为单一用途制造抽象。

## 三、先建立能裁决取舍的体验原则

“简洁、优雅、友好”本身无法指导设计评审。建议将 Metis 的原则写成以下可执行的判断规则。

### 3.1 上下文始终明确

用户在任何页面、审批、错误和通知中，都应知道当前是哪台主机、哪个项目、哪个会话。跨设备后仍然重新接入原主机，不把“接续”表现成复制或迁移。

**裁决规则：**如果两个方案只能通过隐藏作用域来减少界面元素，选择保留作用域的方案。

### 3.2 内容前进，工作台退后

当前任务需要的对话、代码和差异应具有最高视觉权重；导航、辅助元数据和装饰性元素降低存在感。密度来自有效信息和稳定对齐，不来自同时点亮所有控件。

**裁决规则：**减少视觉重量优先于减少信息；先调整位置、对齐、字重和表面，再使用颜色、边框和阴影。

### 3.3 注意力只用于可行动事项

“正在运行”不等于“需要用户处理”。待审批、待输入、失败且可恢复、完成但待审查，与后台正常运行应具有不同的注意层级。

**裁决规则：**例行 token、工具成功和后台进度不弹全局通知；需要用户决定的事项必须清晰可见并可直达。

### 3.4 状态诚实，恢复可达

执行完成不等于验证通过，验证通过不等于用户已接受；断连不等于任务失败，停止不等于撤销，旧快照可读不等于仍可执行实时动作。

**裁决规则：**不能用更乐观、更模糊的文案换取短暂好感。任何错误都要说明保留了什么、未知什么、下一步是什么。

### 3.5 高频操作高效，高级细节渐进展开

常用动作应有稳定入口和键盘路径，菜单、命令面板、按钮和快捷键共享同一动作语义。原始日志和诊断默认可达但不必全部展开；高风险审批的参数、目标和后果不能因“渐进披露”而被隐藏。

**裁决规则：**命令面板是效率增强，不是藏匿常用审批、停止和审查入口的地方。

### 3.6 可访问性是组件契约，不是末端修补

键盘、焦点、对比度、非颜色提示、文本缩放和减少动效在组件设计阶段定义。流式正文、状态播报和系统通知分别设计，避免逐 token 打断辅助技术用户。

**裁决规则：**核心流程存在键盘或辅助技术阻断时，不能用视觉评分或平均满意度抵消。

## 四、把方法变成可重复的交付流程

| 阶段          | 必做产物                                                   | 通过条件                                                                                                                                                                    |
| ------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 定义问题   | 目标用户、真实任务、风险、成功标准、现有模式               | 能用用户结果描述问题，而不是只写“新增某面板”。                                                                                                                              |
| 2. 探索方向   | 少量完整流程方案、真实内容、状态流、焦点路径               | 比较的是端到端取舍，不是几张无上下文组件图。                                                                                                                                |
| 3. 压力测试   | 主页面、极端内容、空/错/加载、窄窗口、中文、明暗主题       | 同一方案在主要视图和状态下仍成立。Linear 在大规模实现前也先进行主要页面压力测试，再定义组件行为。[Linear 2024 改版](https://linear.app/now/how-we-redesigned-the-linear-ui) |
| 4. 定义契约   | 组件 API、插槽、状态矩阵、键盘与焦点、语义令牌、内容规则   | 新视觉决策不散落在页面；行为和无障碍可测试。                                                                                                                                |
| 5. 垂直实现   | 一条真实任务链及所需最小组件、动作和测试                   | 不以组件数量或设计稿完成度代替可用流程。                                                                                                                                    |
| 6. 评审与验证 | 设计评审、工程评审、自动测试、辅助技术检查、形成性用户测试 | 探索后、最终实现前完成系统评审；发布后的问题能回到具体负责人。                                                                                                              |
| 7. 发布与演进 | API/行为/视觉变更说明、弃用与迁移、反馈和指标基线          | Stable 不直接删除；主题和视觉回归不能只因 Rust API 兼容就放行。                                                                                                             |

治理不需要委员会，但需要最终裁决者。NN/g 对设计系统维护者的建议包括：在探索之后、最终实现之前评审，提供低摩擦贡献渠道，并在真实需求与全局一致性之间做判断。[Your Design System Needs an Enforcer](https://www.nngroup.com/articles/design-system-enforcer/) Metis 可以由一名体验负责人和一名工程负责人共同批准 Stable，避免“所有人都同意才行动”，也避免个人偏好替代原则。

### 设计工具与代码的正本边界

- 视觉工具用于探索、比较和沟通，不手工维护第二份行为规则。
- MVP 先以 Rust 中的 Metis 语义令牌为唯一正本，`ResolvedTokens`、GPUI Theme 和测试数据都只能单向派生，不能分别手改。优先复用上游已有语义，只增加 Metis 特有的领域语义。
- 出现真实的设计工具或外部主题交换需求后，再采用 DTCG 作为交换格式。DTCG 2025.10 定义了 JSON、类型、别名、组合令牌和 `$deprecated`，但它是稳定的 Community Group Report，**不是 W3C Standard**。[DTCG 2025.10](https://www.designtokens.org/tr/2025.10/format/)
- Rust 组件、动作注册和测试是行为正本；产品文档只保存原则、模式和原因。
- 引入视觉工具变量后，同样从令牌正本单向生成或同步，避免人工抄值。Linear 2026 年也采用应用内调色工具与 JSON 导入 Figma 的闭环，而不是在设计和代码之间反复手工同步。[Linear 2026 刷新](https://linear.app/now/behind-the-latest-design-refresh)

## 五、可扩展架构：稳定语义，分层变化

### 5.1 五层职责

| 层         | 负责什么                                                   | 主要变化方式                             |
| ---------- | ---------------------------------------------------------- | ---------------------------------------- |
| 体验语义   | 主机、项目、会话、执行、审批、连接、变更、验证和审查的含义 | 经产品决策演进，不能由主题覆盖。         |
| 工作台骨架 | 导航、主工作区、辅助区域、浮层，以及它们的组合和焦点关系   | 通过少量布局预设和区域组合扩展。         |
| 组件与模式 | 按钮、列表、对话框、审批、会话摘要、差异审查等行为与状态   | 类型化 API、组合、受控状态、生命周期。   |
| 语义令牌   | 表面、前景、边框、焦点、状态、排版、间距、圆角、动效等意图 | 由主题解析为不同值，名称和含义保持兼容。 |
| 视觉主题   | 色值、字体、尺寸刻度、密度、圆角、阴影和动效参数           | 在对比度、命中区和减少动效等约束内替换。 |

“无样式行为组件”证明了行为与外观分离的价值：Radix 将键盘、焦点等困难行为留在组件内部，把视觉样式交给上层。[Radix Primitives Introduction](https://www.radix-ui.com/primitives/docs/overview/introduction) 这里借鉴的是分层思想，不是把 Web/Radix API 搬进 GPUI。

### 5.2 主题可以改变什么，不能改变什么

| 主题可以改变                         | 主题不能改变                       |
| ------------------------------------ | ---------------------------------- |
| 明暗色板、强调色、语义状态的实际颜色 | “审批”“危险”“离线”“已过期”的含义   |
| 字体与字号刻度、间距和密度预设       | 页面信息架构、内容、动作及授权范围 |
| 圆角、边框、表面和有限阴影           | 键盘路径、焦点恢复、选择或禁用行为 |
| 图标造型和动效参数                   | 非颜色提示、减少动效和状态播报要求 |
| 语义令牌到原始值的映射               | 公共组件 API 和交互契约            |

因此，主题自由的正确形式不是“开放任意样式覆盖”，而是“**同一语义令牌图的另一组合法值**”。主题不改变信息架构、区域语义、内容、动作、授权、公共组件 API 和键盘行为；字体、间距和密度变化可以触发布局重算与重排，但当前实体、焦点、文本选择、滚动锚点和待处理上下文必须保留。主题测试还要覆盖运行时切换后的溢出、键盘路径、焦点恢复与滚动位置。

### 5.3 以三层令牌作为起点

Primer 使用 Base、Functional、Component/Pattern 三类，基础色只供引用，Functional 是主要消费层，组件令牌保持有限。[Primer Color Usage](https://primer.style/product/getting-started/foundations/color-usage/) Spectrum 同样要求消费者优先解析语义层，只有通用语义无法表达时才增加组件专属令牌。[Understanding Spectrum Tokens](https://opensource.adobe.com/spectrum-design-data/articles/understanding-spectrum-tokens/)

建议 Metis 采用：

- **Primitive**：色阶、原始字体和尺寸刻度，原则上私有；
- **Semantic**：`surface`、`foreground`、`border`、`focus`、`attention`、`danger`、间距、密度和动效，作为产品与组件的主要接口；
- **Component/Pattern**：仅保留确有特殊内部结构的少量令牌，默认组件私有。

依赖方向固定为 `Primitive → Semantic → 少量组件令牌 → 组件 → 模式/页面`。新组件先复用语义令牌，出现真实复用证据再抽象新令牌，避免把每个 GPUI 属性都变成一种公共承诺。

内部主题需要解析、回退和实际合成颜色的对比度测试；对外提供主题文件时，再增加 schema 版本、类型检查、缺失和循环引用检查、未知键诊断及稀疏覆盖。语义令牌的兼容性与原始色值的调整应分别发布和审查。

### 5.4 组件契约比“可配置属性很多”更重要

每个公共组件至少定义：

1. 目的、适用和不适用场景、术语与内容规则；
2. 类型化属性、默认值、事件、受控状态和非法组合；
3. 命名插槽及允许组合的内容，避免为每个页面增加布尔变体；
4. 默认、悬停、按下、焦点、选中、禁用、加载、空和错误等适用状态及优先级；
5. 键盘、焦点进入/离开/恢复、指针操作、溢出、长文本和异步取消；
6. 所消费的语义令牌，不允许调用方任意选择业务颜色；
7. 可访问名称、角色、状态、值和动作；
8. 测试矩阵、负责人、成熟度、替代者和迁移说明。

优先组合小型、明确的组件，不建立一个包装所有 GPUI 控件的巨型适配层。只有需要不同内部结构或产品语义时，才下沉到行为层实现 Metis 自己的组件。

### 5.5 动作与区域是两个高价值扩展点

**动作注册表。** 按钮、上下文菜单、命令面板和快捷键引用同一动作定义，包括名称、作用域、可用性、危险级别和实际执行入口。这样新增动作不会形成四套逐渐漂移的实现。Raycast 的高层 UI 将 `List`、`Detail`、`Form` 与 `ActionPanel` 组合，动作可直接关联快捷键，体现了受约束组合带来的整体一致性。[Raycast User Interface](https://developers.raycast.com/api-reference/user-interface)

**稳定区域与面板注册。** VS Code 将工作台区分为 containers 和 items，说明复杂功能可以依托稳定容器扩展。[VS Code UX Guidelines](https://code.visualstudio.com/api/ux-guidelines/overview) Metis 应吸收区域模型，但首版只提供少量经过设计的布局预设，不开放任意拖拽、任意 Web 内容或每个功能自创工具栏。面板使用稳定 ID、版本化布局数据和未知面板回退，尺寸与活动视图可以恢复。

### 5.6 生命周期与例外

采用 `Draft → Preview → Stable → Deprecated → Removed`。Stable 的公共 API、语义令牌和主题格式必须有兼容边界；弃用记录包含原因、替代者、引入版本、计划删除版本和迁移路径。

视觉变化也要进入发布记录。令牌值即使不改变 Rust API，也可能造成对比度或布局回归。所有“仅此页面例外”都应记录范围、理由、负责人和回收条件，不允许永久临时分叉。

## 六、视觉与产品基准：借鉴机制，不拼贴皮肤

| 产品                                       | 值得借鉴                                                                           | 不应照搬                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Linear                                     | 导航退后、内容前进；减少无意义图标和分隔线；保留密度而降低压迫感；主要页面压力测试 | 紫色品牌识别、issue 信息架构、过低对比的小字，以及把重设计当成唯一解法 |
| Raycast                                    | 搜索—选择—动作—反馈闭环；上下文动作与快捷键可见；克制的轻量反馈                    | 将持续工作台压缩成启动器，把常用审批藏进命令面板，或依赖玻璃材质       |
| Zed                                        | 原生 GPUI 工程、语义表面、有限阴影、上下文体感键位、可恢复面板                     | 完整配置面、特定字体组合，以及把源码里的候选值当成整个产品已统一的规范 |

Linear 2026 年的更新尤其值得注意：侧栏降低亮度、图标减少、边框变软，但目标不是降低信息密度，而是“保留丰富密度，同时避免压迫感”。[Linear 2026 刷新](https://linear.app/now/behind-the-latest-design-refresh) Zed 的源码则将普通 Surface 和 EditorSurface 设为无阴影，只对 ElevatedSurface 和 ModalSurface 使用阴影，提供了适合原生工作台的层级参考。[Zed elevation.rs，调研时提交](https://raw.githubusercontent.com/zed-industries/zed/f62114596325320f5af71399e441cdb76bb9473b/crates/ui/src/styles/elevation.rs)

### 建议的 Metis 视觉方向：冷静、清晰的工作台

这里的“冷静”不是低对比或缺乏反馈，而是界面只在有意义时争取注意力。

- **表面：**以中性石墨色为主，导航比主内容更安静；普通面板不制造浮起感，阴影只用于真正位于工作区之上的浮层和模态。
- **强调色：**以低饱和雾青作为候选交互色，待处理使用琥珀，失败和危险使用红色；最终色值必须根据真实页面的对比度和品牌原型确定，不在调研阶段锁死。
- **排版：**UI 使用系统无衬线并验证中文回退，代码、路径、行号和时长使用等宽字体；不通过缩小字号制造密度，也不以 10px 作为中文常规元文本。
- **结构：**列表和导航紧凑，对话正文、计划和错误说明保留舒适行距；代码与 Diff 使用完整可用宽度，不套用聊天气泡宽度。
- **形状：**小到中等圆角，边框只表达作用域或交互边界，避免“所有区域都是圆角卡片”。
- **图标：**统一网格、描边和尺寸，状态始终使用“文本 + 图标 + 颜色”，不让抽象图标独自承担含义。
- **动效：**只解释状态与空间变化；流式正文直接追加，不做逐 token 淡入或打字机表演；阅读历史时不移动内容，减少动效下取消非必要位移。
- **识别点：**用一致的“主机 → 项目 → 会话”上下文脊线和清晰的待处理语义形成产品识别，而不是依赖品牌色覆盖所有控件。

候选起点可以采用 4px 间距网格、14–15px 正文、12px 元信息、4/6/8px 的控件/浮层/模态圆角层级，但这些只是原型假设，需要中文、长路径、不同 DPI、文本缩放和高对比模式验证。

## 七、智能体体验：状态语义是设计系统的地基

如果状态模型含糊，再漂亮的组件也无法形成可信体验。Apple 的生成式 AI 指南要求保持用户控制，支持撤销、修改和重试，重大或不可逆行动前取得许可，并在生成期间说明实际正在做什么。[Apple Generative AI HIG](https://developer.apple.com/design/human-interface-guidelines/generative-ai) Google PAIR 同样强调在高风险或用户需要承担责任时保留控制，允许退出、修改和人工回退。[PAIR Feedback + Control](https://pair.withgoogle.com/chapter/feedback-controls/)

### 7.1 必须分开的状态轴

不建议用一个 `会话状态` 枚举承载所有含义。UI 至少应区分：

- **连接：**连接中、实时、重连中、离线，以及最后同步时间；
- **执行：**排队、启动、运行、等待用户、停止中、完成、失败、已停止；
- **审批决定：**待处理、允许、拒绝、过期、不可用，并保留处理者与失效原因；
- **行动执行：**未开始、执行中、成功、失败、取消、结果未知；
- **代码变更：**无变更、提议、已应用、冲突、部分恢复、已恢复、未知；
- **验证与审查：**未运行、运行中、通过、失败、结果过期，以及待审查、已接受、要求修改。

这些是不同的 UI 语义，不要求一次性重建成同样数量的后端实体；可以先映射当前 Harness 和 Metis 已有数据。组合测试必须覆盖“批准 + 执行中”“批准 + 结果未知”“拒绝 + 未执行”和“不可用 + 迟到回答”，并利用现有事件标识与客户端代次防止旧回答覆盖新决定。关键是避免以下错误等价：

```text
执行完成 ≠ 测试通过 ≠ 用户接受
连接断开 ≠ 执行失败
停止执行 ≠ 撤销文件或外部副作用
后台运行 ≠ 需要用户立即处理
生成了补丁 ≠ 补丁已经应用
```

### 7.2 审批是任务内决策，不是通知弹窗

审批至少显示主机、项目、工具、精确参数或变更摘要、外部影响、可逆性和授权范围；允许用户拒绝并说明修正方向。待审批不应阻塞无关页面、日志和差异查看。

审批失效后，例如参数、目标或关联运行变化，或者已在另一设备处理，卡片必须变为不可执行并显示原因，不能简单消失。高风险行动不因为用户出现过审批疲劳就默认改为永久允许。

### 7.3 离开、返回和重连是一等场景

用户返回长任务时，优先看到目标、当前状态、离开期间的变化、待决定事项、验证与审查状态，以及推荐下一步，而不是重读全部 token 流。

重连时保留缓存内容并标注最后同步时间；已知存在的数据加载失败不能显示成普通空状态。无法确认远端行动结果时显示“结果未知”，先重连对账，不自动重放非幂等操作。

Host 是持久历史的正本，工作台只保留有界投影：加载可见窗口附近页面和有限会话，按字节数预算淘汰离屏文本与布局，旧历史通过现有分页接口恢复。缓存淘汰不得丢失 Host 内容，也不能让长期使用时所有会话的原始文本、语法树和 GPU 资源无界驻留。

### 7.4 反馈按上下文分配

Primer 建议少于 1 秒避免闪烁加载状态，长任务尽量后台化，加载指示靠近相关内容，集合增量出现。[Primer Loading](https://primer.style/product/ui-patterns/loading/) VS Code 则建议通知只在必要时出现，进度优先留在相关视图，模态只用于必须立即处理的输入。[VS Code Notifications](https://code.visualstudio.com/api/ux-guidelines/notifications)

因此 Metis 应采用三条通道：

- **内容通道：**回答、代码和工具记录可导航、可回看，不逐 token 主动播报；
- **状态通道：**排队、运行、等待审批、完成和失败等语义变化，前台内联表达；
- **系统通知：**后台高价值、可行动事项，去重并深链到具体会话，不泄露敏感参数。

## 八、可访问性与包容性基线

WCAG 2.2 可以作为结果参考，但原生桌面不能机械照搬 HTML 实现。[WCAG2ICT 2.2](https://www.w3.org/TR/wcag2ict-22/) 是应用 WCAG 到非 Web 软件的指导性 Group Note，不是另一套可宣称符合的标准；它要求通过平台无障碍服务暴露对象、属性、动作和事件，并强调真实辅助技术测试。

建议将以下内容纳入每个组件和关键流程的验收矩阵：

- **键盘与焦点：**所有功能可键盘完成，无键盘陷阱；复合控件内部使用方向键；打开、关闭、删除和异步更新后的焦点合理；异步内容不抢焦点。
- **对比度与非颜色提示：**普通文本至少 4.5:1，大文本及理解控件和状态所需的关键非文本信息至少 3:1；状态不只靠颜色表达。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **目标尺寸：**以 24 个平台密度无关单位或满足明确间距例外作为基线，测量命中区而不是图标本身；拖拽必须有非拖拽等价路径。
- **文本与重排：**在 200% 或平台实际能力上限、最小窗口、长中文、长英文、长路径和不同 DPI 下不丢失内容与功能；代码和 Diff 的局部二维滚动不能成为整个工作台拒绝重排的理由。
- **动效：**尊重系统减少动效，取消非必要位移、缩放和循环运动，但保留静态状态信息。
- **流式内容：**正文、状态和系统通知分离；用户阅读历史或选择文本时不强制回到底部。
- **真实平台验收：**自动语义检查之外，使用目标平台的辅助技术检查名称、角色、状态、值、动作和事件；不能以“框架有无障碍功能”替代产品实测。

## 九、GPUI 落地可行性与边界

当前工作区在根 `Cargo.toml:27` 使用 `gpui-kit 0.10.0`。本次核查的发布源码对应提交 [`f697c313`](https://github.com/longbridge/gpui-kit/tree/f697c3133d55c64fa8a5b67926147fb3dadd276d)，不是早期调研中的 0.9.1。

### 9.1 已有基础

固定版本源码已经提供：

- Theme、明暗配置、字体、圆角、阴影、焦点环和部分语义令牌；[Theme](https://github.com/longbridge/gpui-kit/blob/f697c3133d55c64fa8a5b67926147fb3dadd276d/crates/component/src/theme/mod.rs)
- Button、Input、List、Tabs、Popover、Dialog、Command、Resizable、Dock 等基础能力；
- TextView、Editor、Diff，以及 Markdown 扩展和 Diff annotation/decoration 插槽；
- GPUI Action、KeyBinding、FocusHandle、AccessKit 和 headless 交互测试；
- Motion token、系统减少动效读取及图标替换能力。

因此，源码层面未发现“GPUI 为骨架、Metis 自有语义令牌和业务契约为核心”的阻断，暂不需要另建 UI 框架；最终可行性仍由后续关键探针确认。

### 9.2 不能误认为已经自动获得的能力

- 上游存在 typography/spacing token 类型，不代表所有内置组件都已完整消费这些尺度；Metis 仍需持有自己的完整解析后令牌快照。
- `ThemeMode` 只有 Light 和 Dark，跟随系统及三态偏好需要应用管理；Theme 是 App 全局，不是每个窗口独立主题。
- 根节点 `StyleRefinement` 不等于可以任意修改组件内部结构；需要不同结构时应使用公开插槽或 GPUI Base 行为层。
- Command 提供界面和基础匹配，业务动作、权限、异步取消、排序和频率学习仍由 Metis 负责。
- Resizable 的键盘可访问性、复杂产品组件的无障碍语义和真实辅助技术效果需要补充与实测。
- 上游 headless 语义快照不是像素测试，现有 Metis 测试也没有形成关键页面的视觉 golden 体系。
- Editor 的性能说明存在不同口径，必须按真实文件、语言、诊断、折叠、流式更新和 DPI 建立自己的基准。
- 不可信智能体与工具 Markdown 必须在单一 TextView 适配边界收紧默认行为：使用 `.markdown_raw_html(false)` 关闭 raw HTML；使用 `.image_source` 默认拒绝图片或按 scheme、字节数和像素上限放行；使用 `.on_link_click` 拦截默认打开行为，只允许明确批准的 scheme，并展示目标及必要确认。为 raw HTML、HTTP(S)、`data:`、未知 scheme 和恶意超大图片增加边界测试。

### 9.3 推荐工程结构

```text
Workbench application
├── ThemeController
│   ├── System / Light / Dark 用户偏好
│   ├── Metis ThemeSpec 与完整 ResolvedTokens
│   └── GPUI Theme 同步
├── Action / Command / Focus
│   ├── 统一动作定义与上下文体感键位
│   └── 面板、会话和浮层切换后的焦点恢复
├── 通过 gpui-kit 使用 Component
│   ├── 基础控件、Command、List、Dialog
│   └── TextView、Editor、Diff
├── 少量 Metis 产品组件
│   ├── 会话、审批、连接、待处理事项
│   └── 明确的可访问性行为补充
└── 必要时通过 gpui-kit 使用 Base
    └── 需要不同内部结构，而不只是换颜色时
```

继续遵循架构决策记录 0006，只依赖 `gpui-kit` 及其重新导出的 Component/Base，不新增 `gpui`、`gpui-component` 或 `gpui-base` 直接依赖。若未来确需例外，应先修改架构决策并履行依赖审查。

不建议为“未来可能换 UI 框架”包装所有控件。包装应解决真实的业务语义、稳定 ID、无障碍契约、命令绑定或测试问题，而不是预先制造灵活性。

## 十、验证：把“好设计”拆成不同证据

不能用组件覆盖率证明体验优秀，也不能用少数用户说“喜欢”证明扩展性。建议保留四组独立指标。

### 10.1 一致性与演进健康度

- 可标准化界面中系统组件和语义令牌的采用情况；
- 裸色值、魔法尺寸、页面私有交互和重复动作的审计结果；
- 活跃例外、过期例外、Deprecated 调用和迁移完成情况；
- 未经批准的视觉差异及关键交互回归数。

这些指标用于发现系统漂移，不应合成一个掩盖问题的“设计质量总分”。

### 10.2 用户结果

关键任务至少包括：冷启动并准备环境、添加合法项目、从缺少 Git、无效目录或启动超时中恢复、创建并继续会话、阅读流式内容、停止误操作、判断并处理审批、定位并审查改动、断连后恢复，以及从另一设备找出待处理事项。

记录任务成功率、完成时间、误操作、恢复成功率和任务后主观难度；高风险任务还要单独统计误批准、重复执行和用户修改丢失。另以“冷静、清晰、可信、高效”等产品属性收集感知反馈，而不是只问“是否美观”。

NN/g 区分小样本形成性测试与定量研究：约 5 人适合发现问题、修复和复测，总体比例和精确基准需要更大样本及置信区间。[5 Users: Qual vs Quant](https://www.nngroup.com/articles/5-test-users-qual-quant/) Metis 应把每轮小样本测试用于改进，不把“5 人中 4 人成功”包装成普遍成功率。

### 10.3 工程测试分层

1. **纯逻辑：**令牌解析、主题回退、对比度、动作可用性、状态转换、布局迁移；
2. **Headless 交互：**真实组件事件、键盘、焦点、无障碍属性、布局边界、重复与乱序事件，以及主题或密度切换后的焦点和滚动锚点；
3. **受控视觉测试：**固定字体、窗口、DPI、主题、密度和减少动效，对少量命名的高风险场景做人工审批的图像比较；不做页面、状态和所有环境轴的笛卡尔积，并限制产物保留期限；
4. **真实平台专项：**输入法、剪贴板、系统字体、文本缩放、高对比、屏幕阅读器和真实 GPU；
5. **用户验证：**固定数据和确定性流式回放，避免模型延迟与随机输出污染设计比较。

### 10.4 性能体验

“流畅”需要转化为输入和更新体验，而不是动画数量。建议将本地点击、按键和停止请求的可见反馈目标设为下一次渲染且力争 100ms 内；远端模型和主机耗时应单独显示，不能把网络等待伪装成本地无响应。流式期间重点测量输入延迟、滚动位置、选择稳定性和长会话内存，而不是追求装饰性帧率指标。

## 十一、用未来变化压力测试骨架

可扩展性应通过几个具体变化验证，而不是预测所有需求。

| 未来变化                               | 应保持不变                             | 允许变化的部分                         |
| -------------------------------------- | -------------------------------------- | -------------------------------------- |
| 里程碑 1 的单项目扩展到里程碑 2 多主机 | 会话、审批、编辑和 Diff 的内部模式     | 导航增加主机层级，增加跨主机待处理聚合 |
| 从另一设备接入                         | 原主机会话和审批语义                   | 返回摘要、同步状态和设备本地布局       |
| 新增一个产品面板                       | 区域、焦点、动作、空/错/加载和主题契约 | 面板内容及有限布局预设                 |
| 新增明暗之外的视觉主题                 | 页面骨架、组件 API、状态含义和交互行为 | 语义令牌的解析值                       |
| 修改一种状态颜色                       | 业务状态名称和其他组件                 | 对应语义令牌及视觉快照                 |
| 移除或替换组件                         | 用户任务和数据语义                     | 经 Deprecated、迁移和回退完成实现替换  |

工作区持久化也应遵循现有架构边界：主机保存会话、任务和审批；设备保存窗口布局、面板尺寸和本地未保存文本。小屏设备不应直接恢复另一台大屏设备的窗口几何。主题等用户偏好在里程碑 3 可以同步，但设备布局仍应按设备解析和恢复。

## 十二、建议的落地顺序

### 第一步：完成一个设计垂直切片，而非组件宇宙

选择“冷启动并准备环境 → 添加并打开本地项目 → 创建会话 → 流式输出 → 审批 → 审查 Diff”作为第一条切片，使用真实中文、长路径、长代码、错误与重连数据，并覆盖环境准备失败、无效或非 Git 目录、启动超时、取消与重试。以同一骨架探索少量完整视觉方向，比较高保真主工作台、首次启动和审批状态。

通过条件不是“看起来像 Linear”，而是体验原则可辨认、核心流程可理解、主要状态没有缺页，并且团队能解释每个重要视觉决策。

### 第二步：提取最小设计系统

只建立切片需要的语义令牌、基础组件、产品组件和模式；同时提供浅色、深色和高对比验证，形成组件契约模板、动作注册规则和 UI 变更检查清单。

### 第三步：完成关键技术探针

优先验证 GPUI 主题写路径、中文与文本缩放、键盘分栏、AccessKit 与真实辅助技术、不可信 Markdown 内容安全、有界历史投影、长会话流式性能、Editor 大文件性能，以及受控像素测试链路。探针失败应先调整实现方案，不能让视觉稿承诺无法交付的行为。

### 第四步：形成性测试后再扩大实现

让目标开发者完成停止误操作、拒绝危险行动、恢复连接和审查改动等任务，修复问题并复测。之后再扩展到更多页面和组件，保留相同任务作为里程碑间的体验基准。

### 明确不做

- 不先建设完整组件宇宙、公共主题工具链或复杂治理机制；
- 不为了“可扩展”开放任意样式、面板位置和万能组件配置；
- 不复制 Linear 的品牌皮肤，不提前绘制所有未来页面，而是用未来变化做骨架压力测试；
- 不把规范、框架、自动扫描或截图全绿当成优秀设计和真实可访问性的替代品。

## 最终建议

采用“**受控扩展的语义化设计系统**”作为总方向。下一步制作第一条端到端高保真垂直切片，并让体验与工程评审分别检查；视觉品味应在真实工作台、真实内容和真实状态中验证，而不是在孤立色板上决定。
